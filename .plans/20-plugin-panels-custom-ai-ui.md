# Панельные плагины и кастомный AI-интерфейс (Plugins v2/v3)

Дизайн по итогам разбора плагинной системы bb (github.com/ymichael/bb, клон изучен 2026-08-24) и запроса Миши: «софтинки» должны жить внутри приложения, а не на localhost; интерфейс приложения должен собираться под пользователя, вплоть до кастомного чат-интерфейса поверх любого харнесса.

## Что мы узнали из bb — и что берём/не берём

**Как устроено у них.** Плагин bb — npm-пакет с TypeScript-кодом в трёх ролях: `server.ts` исполняется **внутри процесса сервера** (полное доверие, без песочницы), `app.tsx` — React-бандл, **динамически импортируемый прямо в страницу приложения** (общий React, общий дизайн-система, ~20 именованных слотов с crash-изоляцией), `host.ts` — worker на удалённых машинах. Side chat, workflows, crons, inline previews, провайдеры агентов — всё плагины.

**Три их решения, которые дают «магию» и которые мы воспроизводим:**
1. **Чат экспортируется плагинам, а не переизобретается.** Их side chat — ~700 строк: скрытый форк треда + хост-компонент `ThreadChat` с параметрами (`variant="compact"`, `permissionPolicy="inherit"` — плагин структурно не может расширить права). Таймлайн и рендер сообщений всегда за хостом — «лента читается едино».
2. **Само-расширение = скилы.** 2 740-строчный authoring-skill в системном наборе + **сервер-генерируемый** скилл со списком команд установленных плагинов (перегенерируется при каждом install/toggle). Агент знает и «как писать плагины», и «что уже установлено».
3. **События observe-only, fire-after-commit** — хук не может ничего заблокировать; reload атомарный (упавшая фабрика оставляет старые регистрации); статус `needs-configuration` — первоклассное состояние. (Мы уже в этой парадигме с v1.)

**Что сознательно не берём:** исполнение кода плагина в процессе демона и в странице приложения. bb честно пишет «plugins are full-trust code in every runtime» — их аудитория разработчики, расширяющие свой собственный IDE. Наш контекст — hosted-продукт с платными клиентами. Показательно: единственное место, где bb постоянно исполняет **агентский** код (workflow-скрипты), они завернули в QuickJS-WASM без FS/сети/часов. Это наш прецедент: граница доверия — декларативный манифест; UI-код плагина — только в sandboxed iframe. Бонус: манифест стареет лучше кода (bb тащит целый SDK-compat аппарат — `experimental_`-префиксы, мажоры SDK, `needs-update` бандлы; декларативному манифесту это не нужно — неизвестные ключи просто игнорируются).

## Фаза A — Панельные плагины (декларативные «софтинки»)

Манифест получает секцию `panel`:

```json
{
  "name": "Deploy dashboard",
  "panel": { "title": "Deploys", "path": "panel/index.html" },
  "crons": [
    { "id": "refresh", "every": "15m",
      "run": { "kind": "shell", "command": "~/scripts/collect-deploys.sh > ~/.unowork/userdata/plugins/deploy-dash/panel/data.json" } }
  ]
}
```

- Плагин с `panel` становится **директорией** `plugins/<id>/` (манифест `plugin.json` внутри + статические ассеты). Плоские `<id>.json` без панели продолжают работать — обе формы читает один реестр.
- Демон раздаёт `GET /api/plugins/<id>/panel/*` (auth: пользовательская сессия, как attachments; заголовки `nosniff`, CSP `default-src 'self'`).
- Панель рендерится вкладкой правой панели через **sandboxed iframe** (`sandbox="allow-scripts"`, opaque origin) — ровно так bb рендерит untrusted HTML в inline-vis. Вкладка per-project, видна в Extensions.
- «Живой» дашборд без всякого API: cron того же плагина перегенерирует `data.json`/HTML, iframe поллит fetch'ем соседний файл.
- В pluginInstructions добавляем: «результат-приложение без backend → панельный плагин, не localhost» + по образцу bb — **сервер-генерируемый блок со списком установленных плагинов** (агент видит, что уже есть, и правит, а не дублирует).

## Фаза B — Мост панель ↔ приложение

Узкий типизированный postMessage-API (фиксированный словарь, как browser bridge; никакого доступа к DOM приложения):

- `uno.openFile(path)` / `uno.openUrl(url)` — навигация в соседние вкладки;
- `uno.runAction(actionId, params)` — вызвать декларативное действие из манифеста (shell с фикс. командой; параметры — только whitelisted-подстановки);
- `uno.sendToThread({ text, threadTag })` — **создать/дописать тред от имени плагина** (атрибуция `origin: plugin`, как `origin: manager` сейчас; тот же паттерн, что `threads.spawn` у bb);
- `uno.subscribe(eventPattern)` — observe-only события оркестрации (тот же матчер, что у hooks) → postMessage в iframe.

После B панель уже может быть «пультом агента»: кнопки, формы, свои визуализации, отправка промптов и живая реакция на события — без рендера чата.

## Фаза C — Кастомный AI-интерфейс («чат приезжает в панель»)

Урок bb: не давать плагину рендерить сообщения — дать хост-чат как встраиваемый примитив.

- Выносим текущий ChatView в переиспользуемый хост-компонент `EmbeddedThreadChat` (variant `compact`, `permissionPolicy: inherit` — сужать можно, расширять нельзя).
- Манифест: `"panel": { "chat": { "mode": "compact", "threadTag": "deploy-dash", "visibility": "answers-only" } }` — рядом с iframe хост рендерит компактный чат, привязанный к треду плагина.
- `visibility` — ответ на «не каждое действие агента показывать»: это **фильтр отображения хостового таймлайна** (`full` | `answers-only` — только финальные ответы и вопросы-к-пользователю | `hidden` — только композер), а не плагинный рендер. Шум прячется, лента остаётся хостовой.
- Итоговый UX: пользователь живёт в правой панели в focus-режиме — сверху его кастомный интерфейс (HTML, сгенерированный агентом), снизу компактный композер и только ответы; центральный чат свёрнут. Харнесс любой (Claude/Codex/OpenCode/Uno) — «AI-интерфейс» это данные, а не форк фронта.
