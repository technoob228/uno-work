# Uno Work — fork of T3 Code

Этот репозиторий — форк [pingdotgg/t3code](https://github.com/pingdotgg/t3code), кастомизированный под продукт **Uno Work**. Основной апстрим-документ — [`AGENTS.md`](./AGENTS.md). Здесь описаны только наши изменения относительно апстрима.

Продуктовый план Uno Work лежит в [`UNO_ROADMAP.md`](./UNO_ROADMAP.md).

## Запуск

```bash
bun dev:desktop   # запускает web + Electron одновременно (через scripts/dev-runner.ts)
bun dev           # ТОЛЬКО web — Electron не стартует
bun fmt && bun lint && bun typecheck  # перед коммитом
```

`bun --filter '@t3tools/desktop' dev` напрямую **не работает** — `VITE_DEV_SERVER_URL` инжектится только через корневой `dev-runner`.

Если приложение надо оставить запущенным после ответа агента, не держать его в интерактивном PTY tool-session. Запускать как user launchd job:

```bash
launchctl submit -l xyz.unowork.dev -o /tmp/uno-work-dev.log -e /tmp/uno-work-dev.err -- /bin/zsh -lc "cd '$PWD' && exec $(command -v bun) dev:desktop"
```

Остановить такой dev-запуск:

```bash
launchctl remove xyz.unowork.dev
```

После `bun dev:desktop` не считать запуск успешным только по Vite URL. Обязательный smoke:

```bash
curl -I http://127.0.0.1:5733/
curl http://127.0.0.1:13773/.well-known/t3/environment
```

Если Electron показывает белый экран, полностью остановить и заново запустить `bun dev:desktop`. После изменений в `apps/desktop/src/main.ts` не полагаться на hot-restart watcher: он может оставить `dev-electron` живым без корректно поднятого окна/backend. Для диагностики смотреть процессы `dev-electron`, `--t3code-dev-root` и `apps/server/dist/bin.mjs`; браузерная проверка `5733` сама по себе не доказывает, что desktop shell жив. Успешный desktop smoke должен показать в Electron-логе `[desktop] renderer snapshot` с `content-ready` и `rootTextLength > 0`.

Dev Electron включает локальный CDP endpoint для Playwright: `http://127.0.0.1:9223`. Он нужен агентам, чтобы управлять уже открытым Uno Work/browser-pane через `chromium.connectOverCDP(...)`, а не отдельным браузером без профиля. Порт слушает только localhost; переопределить или отключить можно через `UNO_WORK_ELECTRON_REMOTE_DEBUGGING_PORT` (`0`/`false`/`off` отключает).

### 2. Dev mode toggle

`apps/web/src/devMode.ts` — простой хук + storage-event на `localStorage.ui_dev_mode`. Скрывает технические кнопки от обычных пользователей.

Кнопка-тоггл (`<CodeIcon>`) живёт в `ChatHeader` слева, рядом с бейджем проекта. По клику переключает `ui_dev_mode` и через `window` event синхронизирует все потребители.

С 29.10 тоггл есть и в конце ряда мест сайдбара D (`DevModePlace` в `sidebar/SidebarDParts.tsx`: горит, пока включён, `aria-pressed`). Иконки этого ряда (28 px) при наведении выпускают название, соседи справа сдвигаются; если названию не хватает места в ряду (Automations, Dev mode рядом с Needs you), вместо него обычный тултип, без многоточий (`placeNamesThatFit` в `sidebarD.logic.ts`). Закреплённое приложение с Home-виджетом показывает виджет карточкой рядом с пином (`sidebar/PinPeek.tsx`).

Под `{devMode && …}` спрятаны:

- `ChatHeader`: ProjectScripts, OpenInPicker, GitActions (Commit & push), Terminal toggle, Diff toggle.
- `ChatView`: `BranchToolbar` (только когда есть git-репо).

### 4. Mutual exclusion: Diff panel ↔ Preview pane

В `apps/web/src/routes/_chat.$environmentId.$threadId.tsx` — два `useEffect`, которые гарантируют, что в один момент открыта только одна панель: открыли Diff → закрыли Preview, и наоборот.

### 5. Click-to-preview routing для «Changed files»

`ChatView.onOpenTurnDiff` (см. `apps/web/src/components/ChatView.tsx`) роутит клик по файлу в карточке «Changed files»:

- `kind === "text"` (код) → старый Diff (TanStack Router search params).
- Всё остальное (md/html/pdf/csv/json/image/xlsx/unknown) → `usePreviewPane().openFile(...)`.

**Важно про путь:** `node.path` из `ChangedFilesTree` — project-relative (`test.html`). FileBrowser передаёт **абсолютный** путь. Поэтому в `onOpenTurnDiff` мы вручную джойним с `gitCwd` (корень проекта, с учётом worktree). Без этого Electron резолвит относительный путь от своего `cwd` (корень репозитория) и получает ENOENT.

- **Web:** `apps/web/src/components/preview/BrowserPane.tsx` — Electron `<webview>` с тулбаром (назад/вперёд/обновить/адресная строка/автозаполнение/открыть внешне), все вкладки смонтированы (скрытые `display:none`). `browserUrl.ts` — нормализация ввода в URL (+ тесты). `PreviewPaneContext` — `openUrl`/`updateBrowserTab`, `currentProjectKey`. Инструкции про браузер (+ ссылка на `getuno.xyz/llms.txt`) — `provider/browserInstructions.ts`: Claude через `systemPrompt.append`, Codex через `developer_instructions`, OpenCode/Uno через `instructions`-файл в `OPENCODE_CONFIG_CONTENT`.
- **Настройки:** раздел «Browser» (`settings.browser.tsx` + `BrowserSettingsPanel.tsx`) — выбор профиля (аккаунт/проект) и менеджер сохранённых входов.

### 7. Плагины — само-расширяемость (Settings → Extensions)

Агент, работающий внутри Uno Work, может расширять сам harness: плагин — это `<id>.json` **или** директория `<id>/plugin.json` (с ассетами рядом) в `<baseDir>/userdata/plugins/` (в dev-режиме `<baseDir>/dev/plugins/`). Демон следит за директорией и подхватывает изменения без рестарта. Манифест декларативный: **hooks** (реакция на события оркестрации → shell-команда) и **crons** (`schedule` — 5-польный cron, либо `every` — интервал, минимум 1m). Никакого исполнения чужого JS в процессе демона — только spawn `/bin/sh -c` с таймаутом (дефолт 60 с, максимум 10 мин) и ограничением параллелизма (4). Окружение команды минимальное: `PATH`, `HOME`, `UNO_PLUGIN_*` (с 27.09, `buildPluginCommandEnv`), env демона с ключами не наследуется.

- **Контракты:** `packages/contracts/src/plugins.ts` (`PluginManifest`, `ServerPlugin`, `PluginsSnapshot`, `PluginsError`); RPC `server.listPlugins` / `server.setPluginEnabled` / `server.approvePlugin` / `plugins.issuePanelUrl` / `subscribePlugins` в `rpc.ts`.
- **Сервер:** `apps/server/src/plugins/` — `cron.ts` (парсер + матчинг, тесты), `PluginRegistry.ts` (загрузка/watch/снапшоты, паттерн `serverSettings.ts`), `PluginRuntime.ts` (подписка на `OrchestrationEngine.streamDomainEvents` + 30-сек cron-свип; каждый запуск логируется `plugins.action.completed` и записывается в историю для UI), `pluginInstructions.ts` (блок системного промпта). Путь `pluginsDir` — в `config.ts`; старт — `serverRuntimeStartup.ts`; слои — `server.ts`.
- **Инструкции агенту** инжектятся во все четыре драйвера рядом с browser-инструкциями (Claude — `appendSystemPrompt`, Codex — `appendDeveloperInstructions`, OpenCode/Uno — общий `uno-browser-instructions.md` через `extraSections`). Благодаря этому «сделай, чтобы приложение …» превращается в плагин без участия человека.
- **UI:** Settings → Extensions (`settings.extensions.tsx` + `ExtensionsSettingsPanel.tsx`): список плагинов, вкл/выкл (правит `enabled` в файле), ошибки невалидных манифестов, последние запуски (live через `subscribePlugins`).
- Хуки исполняют команды с env `UNO_PLUGIN_EVENT` (JSON события), `UNO_PLUGIN_EVENT_TYPE`, `UNO_PLUGIN_ID`, `UNO_PLUGIN_TRIGGER`.

**Панельные плагины (фаза A ТЗ `.plans/20-plugin-panels-custom-ai-ui.md`).** Плагин-директория может объявить `"panel": { "title": ..., "path": "panel/index.html" }` — статическую «софтинку» во вкладке правой панели: агент пишет HTML+inline JS, а cron того же плагина обновляет `data.json` рядом. Никаких localhost-серверов.

- **Раздача:** `apps/server/src/plugins/http.ts` — `GET /api/plugins/:pluginId/panel/<token>/*`; `panelPaths.ts` — резолв путей (entry-файл манифеста и его директория как корень, защита от traversal, тесты). Заголовки: MIME по расширению, `X-Content-Type-Options: nosniff`, CSP `self` + inline, `Cache-Control: no-cache`. Плагин выключен/без панели/неизвестен → 404.
- **Auth панели (с 27.09):** панель рендерится в `<iframe sandbox="allow-scripts">` **без** `allow-same-origin`, CSP ответа дублирует это (`sandbox allow-scripts`), сессионную куку её запросы не несут. Поэтому КАЖДЫЙ запрос (документ и субресурсы) идёт по подписанной ссылке `/api/plugins/<id>/panel/<token>/<rest>`: HMAC-токен (секрет процесса демона, привязка к id плагина + `panel.path`, constant-time проверка) выдаёт аутентифицированный RPC `plugins.issuePanelUrl`; токен в пути, поэтому относительные `data.json`/`app.js` наследуют его сами. Документ панели — ≤2 мин от выдачи, остальные файлы — 8 ч. Эвристики по `Sec-Fetch-Dest` больше нет. Код: `plugins/panelTokens.ts`, `plugins/http.ts`, веб — `preview/pluginPanelUrl.ts`.
- **Реестр:** `PluginRegistry.ts` знает обе формы, валидирует `panel` (только директория, относительный путь, файл существует), считает коллизию id ошибкой у обеих форм и перевешивает `fs.watch` на каждую плагин-директорию после reload (плюс дедуп снапшотов — запись `data.json` кроном не будит UI).
- **Одобрение манифестов (с 27.09):** новый плагин и любое изменение манифеста (кроме `enabled`) неактивны — ни хуков, ни кронов, ни панели — пока пользователь не нажмёт «Approve» в Settings → Extensions (показываются команды). Одобряется sha256 канонического манифеста (`plugins/pluginApproval.ts`), RPC `server.approvePlugin {pluginId, manifestHash}` сверяет хэш с текущим файлом. Записи — `<stateDir>/plugin-approvals.json`, каждая подписана HMAC-ключом из secret store (`plugin-approvals-hmac`); неподписанная/поддельная запись = не одобрено. Миграция: при первом запуске (ключа ещё нет) все установленные валидные и включённые плагины записываются одобренными, один раз. Ограничение: агент работает под тем же uid, что и демон, и теоретически может прочитать ключ — настоящее разделение требует отдельного uid для агента.
- **UI:** вкладка `kind: "plugin-panel"` (`PreviewPaneContext.makePluginPanelFile` → `/api/plugins/<id>/panel/`), рендер iframe в `PreviewPane.tsx`, кнопка «Открыть панель» в Settings → Extensions и подменю «Панели» в меню «+» табстрипа (список через `server.listPlugins`).

**Мост панель ↔ приложение (фаза B того же ТЗ).** Панель может управлять приложением через `postMessage`: `{ __unoPanel: 1, id, method, params }` → `{ __unoPanel: 1, id, result | error }`. Методы v1: `openFile`, `openUrl`, `sendToThread`, `subscribe`.

- **Хост:** `apps/web/src/components/preview/panelBridge.ts` (протокол, словарь методов, rate limit 10 вызовов/с на вкладку, фильтр подписок через общий `hookMatches`) + обвязка в `PluginPanelBody` (`PreviewPane.tsx`). Канал — `MessagePort` (с 27.09, `attachPanelPortHost`): на ПЕРВЫЙ `load` iframe хост шлёт `postMessage({type:"uno-panel-init"}, "*", [port2])`, дальше только порт; window-`message` хост не слушает; на любой следующий `load` (фрейм навигировал) порт закрывается и не перевыдаётся. Старые панели на `window.parent.postMessage` мост больше не видят — сниппет в `pluginInstructions.ts` обновлён. Мост создаётся один раз на документ панели, контекст проекта читается из ref — иначе подписки терялись бы при смене контекста.
- **События:** `apps/web/src/environments/runtime/shellEventBus.ts` — fire-after-commit-шина поверх уже существующего `subscribeShell` (публикуется в `runtime/service.ts` после применения события к стору). Панели отдаются только события её проекта, переведённые в точечную нотацию `thread.upserted` / `thread.removed` / `project.upserted` / `project.removed` (сырого потока доменных событий у клиента нет — по WS приезжает проекция с `kind`).
- **`sendToThread`:** (с 27.09 — только после модального подтверждения пользователя с текстом задачи, `createPanelSendConfirmer`; один диалог за раз, отказ → ошибка панели) RPC `plugins.sendToThread` (контракты `PluginSendToThreadInput/Result`), реализация — `apps/server/src/plugins/panelThread.ts`, вызов из `ws.ts`. Тред создаётся в проекте вкладки с заголовком `[<имя плагина>] <threadTag>`; `threadTag` (по умолчанию `panel`) переиспользует живой тред — карта `pluginId+tag → threadId` живёт в памяти `PluginRegistry`, живость проверяется через `ProjectionSnapshotQuery`. `runtimeMode`/`interactionMode` наследуются (переиспользуемый тред — свои, новый — от первого треда проекта; наследовать не от чего → `approval-required`, НЕ `full-access`). Каждый вызов пишется в `recentRuns` (`trigger: "panel sendToThread"`) и логируется; клиент показывает тост «Плагин X отправил задачу агенту».
- **Origin:** `OrchestrationCommandOrigin` стал union — к `{ kind: "manager" }` добавился `{ kind: "plugin", pluginId }`; он проставляется в метаданных всех событий команды, так что event store остаётся аудит-логом и для панелей.
- **Общий словарь паттернов:** `hookMatches` переехал в `@t3tools/shared/pluginPatterns` — одна реализация на хуки демона (`PluginRuntime`) и подписки панели.
- **Харднинг раздачи:** в `plugins/http.ts` добавлена realpath-проверка (файл после разыменования обязан оставаться внутри директории плагина) — симлинк из панельной папки наружу больше не читается неаутентифицированным субресурсным запросом.
- **Инструкции агенту:** `pluginInstructions.ts` содержит готовый JS-сниппет моста (промис-обёртка) и описание методов с ограничениями.

**Кастомный AI-интерфейс (фаза C того же ТЗ).** Панель может попросить хост-чат себе в соседи: `"panel": { …, "chat": { "threadTag": "reports", "visibility": "answers-only" } }`. Вкладка делится на две части — сверху iframe плагина, снизу настоящий чат приложения по треду этой панели. Чат всегда рендерит хост: плагин не рисует сообщения и права треда не расширяет (селектор runtime mode в таком композере скрыт).

- **Тред — один на панель:** RPC `plugins.resolvePanelThread` (`panelThread.ts`, `makePanelThreadResolver`) ходит в ТУ ЖЕ карту `pluginId + threadTag → threadId` в памяти `PluginRegistry`, что и `sendToThread`, но хода не запускает. Общий код обоих RPC — `loadPanelContext` + `resolveOrCreatePanelThread`; наследование `runtimeMode`/`interactionMode` и fallback `approval-required` — как в фазе B. Карта в памяти → после рестарта демона панель заводит новый тред (принято).
- **`EmbeddedThreadChat`** (`apps/web/src/components/chat/EmbeddedThreadChat.tsx`) — обёртка над `ChatView` с флагом `embedded`. **Компромисс, зафиксированный в ТЗ (C1):** `ChatView` — одна функция на ~3.5к строк, где вся обвязка композера (60+ пропсов) вычисляется на месте, поэтому вместо вытаскивания «таймлайн + композер» переиспользуется весь `ChatView`, а `embedded` гасит в нём chrome и эффекты, которые обязаны быть в одном экземпляре на документ: заголовок, `BranchToolbar`, plan sidebar, терминалы, глобальные хоткеи, `setCurrentChatContext`, общий ref композера, автофокус, фокус-режим. ### 8. «Продолжить на другой машине» (Continue on <machine>)

Один чат переезжает с демона, где он живёт, на другой подключённый демон: кнопка в `ChatHeader` (иконка монитор+телефон) и пункт «Continue on another machine…» в контекстном меню треда. Фаза 1 — вручную, по одному треду; примитивы рассчитаны на будущий per-project «Sync».

- **Безопасная версия (0.0.57, решение 15.09, план `.plans/22-workspace-and-safe-continue.md` п.1).** До 0.0.56 снимок пушился `--force --no-verify` в ветку `uno/continue/<threadId>` на `origin`, `.env` копировался по умолчанию, а на цели файлы ложились поверх текущей ветки. Теперь: **ничего не пушится**, код идёт через клиент; `.env` — только по галке (по умолчанию выкл.); на цели — отдельный worktree на новой ветке, рабочая копия пользователя не трогается.
- **Контракты:** `packages/contracts/src/threadContinue.ts`. RPC: `thread.continue.inspect` (цель, read-only: есть ли папка, git ли это), `thread.continue.snapshot` (источник: снимок + bundle, возвращает `transferId`, размер, SHA-256, число чанков, seed, настройки треда, `remoteUrl` только для клона, `envText` только при `includeEnv: true`), `thread.continue.readChunk` (источник) / `thread.continue.writeChunk` (цель) — base64-чанки по 2 МиБ (`THREAD_CONTINUE_CHUNK_BYTES`), лимит bundle 1 ГиБ, `thread.continue.land` (цель), `thread.continue.discard` (любая сторона, best-effort), `thread.continue.complete` (источник). `ThreadContinueError` с machine-readable `reason` (новые: `too_large`, `transfer_not_found`, `transfer_incomplete`, `base_missing`, `worktree_failed`).
- **Версии и совместимость.** Демон с новым протоколом объявляет `capabilities.threadContinueDirect` в дескрипторе окружения. Клиент не стартует, если флага нет у источника или цели (строка «Update Uno Work on <machine>…», у машины в списке — «Needs update»; для неподключённой цели проверка повторяется после коннекта, в шаге connecting). Старые RPC `thread.continue.prepare/receive/cleanup` оставлены в группе только ради совместимости: новый демон всегда отвечает `invalid_request` с текстом `THREAD_CONTINUE_LEGACY_CLIENT_MESSAGE` («обновите приложение»), так что старый клиент (0.0.53–0.0.56) через новый демон ничего не опубликует. Старый демон + новый клиент: клиент видит отсутствие флага и не зовёт методы.
- **Файлы: git bundle через клиент.** `apps/server/src/git/continueTransport.ts`: снимок рабочего дерева (tracked + untracked, без ignored) чекпоинт-машинерией (`CheckpointStore.captureCheckpoint` с `parents`/`message`) в скрытый ref `refs/t3/continue/<transferId>` с родителем HEAD → `git bundle create <file> <ref> --not --remotes` (в bundle только коммиты, которых нет ни на одной remote-tracking ветке источника, + снимок; без remote — вся история) → ref удаляется. Файлы bundle — `apps/server/src/git/continueTransferStore.ts`: `<baseDir>/tmp/continue/{outgoing,incoming}/<transferId>.bundle`, transferId только UUID, запись чанка по offset (повтор чанка обрезает файл, дырка → `transfer_incomplete`), подчистка старше 24 ч при каждом snapshot. Клиент (`apps/web/src/continueOnMachine.ts`) читает чанки с источника и пишет на цель.
- **Цель (`land`).** Проверка размера и SHA-256 → проект: `existing` (зарегистрирован по пути) или `create` (клон по `remoteUrl` — это чтение; без remote — `git init` + вся история из bundle; уже существующий git-клон усыновляется) → модель (до любых git-записей, чтобы отказ не оставлял веток) → `git bundle verify`; если нет базового коммита — `git fetch --all` из remotes цели и повторная проверка, иначе `base_missing` («Pull the latest commits…») → `git fetch <bundle>` в скрытый ref, сверка oid → `git worktree add -b uno/continue/<первые 8 символов id треда>[-N] <baseDir>/worktrees/<repo>/<branch> <baseCommit>` → `restoreCheckpoint` снимка в worktree (изменения остаются незакоммиченными, как на источнике; у unborn-источника ветка стартует прямо со снимка) → удаление ref и входящего bundle → `.env` (если прислан) пишется в новый worktree, не в корень проекта → `thread.create` с `branch`/`worktreePath`, seed, активность `thread.continued.from` (branch, worktreePath, commit, baseCommit).
- **История едет как seed.** `apps/server/src/orchestration/handoff.ts` — общий с Telegram-коннектором модуль: `buildHandoffContext` (Telegram: 12×600), `buildContinueSeed` (40×4k + заголовок «[Continued from <machine>] …»). Сами строки-маркеры преамбулы лежат в `packages/shared/src/handoff.ts` (`@t3tools/shared/handoff`), `handoff.ts` их реэкспортирует — web узнаёт seed по тем же константам. Seed становится первым user-сообщением нового треда и **не** отправляется как ход; `ProviderCommandReactor` через `resolvePendingHandoffSeed` подклеивает его к промпту первого реального хода (у Claude/Codex прошлые сообщения проекции в харнесс иначе не попадают — только OpenCode читает `contextMessages`). В таймлайне (`MessagesTimeline.tsx`, `HandoffSeedBody`) seed рендерится свёрнутой карточкой «Continued from <machine> · N earlier messages» с «Show history»; текст после преамбулы (сообщение из Telegram, пометка о смене модели) виден всегда. Детектор — `isHandoffSeed`/`describeHandoffSeed` в `apps/web/src/continueOnMachine.ts`.
- **Обработчики:** `apps/server/src/orchestration/continueOnMachine.ts` (явные deps, как `plugins/panelThread.ts`), провязка в `ws.ts` (`transfers` = `makeContinueTransferStore({ rootDir: <tempDir>/continue })`, `worktreesDir` из `ServerConfig`). `.env` на источнике: сначала из worktree треда, иначе из корня проекта. Модель — та же, если харнесс установлен, иначе default проекта / auto-bootstrap с пометкой в seed. Origin команд `{kind:"system", component:"thread-continue"}`.
- **Web:** степ-машина connecting (коннект + проверка `threadContinueDirect`) → saving (snapshot) → sending (чанки, прогресс «X MB of Y MB») → preparing (land) → marking (complete) → opening; discard на источнике после land — молча. Чекпоинт прогресса: retry продолжает с первого недошедшего чанка; `transfer_not_found` на источнике сбрасывает снимок (retry снимет новый), `transfer_incomplete` на цели — один автоматический рестарт загрузки / повторная отправка при retry. `ContinueOnMachineDialog.tsx`: у каждой машины «Has this project» / «Project will be added» (машины с проектом сверху) или «Needs update»; под списком — что будет на цели («opens in a separate copy of the project on a new branch. Your files … stay as they are»), подтверждения «Replace them» больше нет; галка «Also copy .env secrets» выключена по умолчанию, с пояснением. Строки — `continueOnMachineCopy.ts`.
- **Тесты:** `handoff.test.ts`; `orchestration/continueOnMachine.test.ts` (fake transport/transfers: снимок без push, `.env` только по флагу и из worktree, too_large, land в worktree на новой ветке, нумерация `-N`, fetch недостающей базы, `base_missing`, `commit_mismatch`, `no_model` до git-записей, clone / `git init` без remote, legacy-отказ); `git/continueTransport.test.ts` (реальный git: неотправленный локальный коммит + правка + новый файл + удаление + ignored едут bundle'ом в новый worktree, рабочая копия цели и её незакоммиченные файлы не тронуты, bare-«GitHub» не изменился; догрузка базы из remote цели; репозиторий без remote → свежий `git init`); `git/continueTransferStore.test.ts` (чанки туда-обратно, повтор/дырка, UUID-валидация, TTL); `apps/web/src/continueOnMachine.test.ts` (порядок шагов, `.env` только с галкой, стоп при старой версии, resume с чанка, рестарт загрузки, гейтинг кнопки). Живая проверка двумя стендовыми демонами — см. отчёт по ветке `feat/safe-continue`.
- **Компромиссы:** worktree на цели чистится по общим правилам копий чатов (раздел 11), как и обычные worktree тредов; ветка `uno/continue/*` на цели — локальная. Список целей — только сохранённые окружения (как раньше), локальный primary-демон целью не предлагается. Если `land` упал после `git worktree add` (например, restore), worktree остаётся — retry возьмёт следующее имя `-N`.

### 12. Чистка копий чатов (worktree cleanup, 0.0.157)

Задача Миши 28.10: в апстриме есть управление хранилищем с автоудалением worktree; у нас всё это спрятано под Advanced, а по умолчанию демон чистит копии сам. Повод: 09.10 бокс на 40 ГБ забился 20+ копиями по ~400 МБ `node_modules`, а облачные диски у нас около 10 ГБ.

- **Сервер:** `apps/server/src/worktreeCleanup/` - `policy.ts` (чистые правила: кого и когда), `worktreeGit.ts` (git и файлы: состояние копии, снимок, `.env*`, удаление, пересоздание), `WorktreeCleanup.ts` (сервис, расписание, отчёт, `WorktreeCleanupLive`). Подключён в `server.ts`, стартует в `serverRuntimeStartup.ts` (reactors.start). Миграции нет (номер 052 не занят).
- **Настройки** `storageCleanup` в `ServerSettings` (все с decoding-default, старые settings.json получают дефолты): `worktreeOnDelete: true`, `worktreeSettledAfterDays: 3` (Done или архив, тишина 3 дня; `0` = сразу, `null` = никогда), `worktreeAfterDays: 14` (любой чат без активности), `worktreeLowDisk: true` (диск < 15% или < 3 ГБ свободно - константы `resourceWarnings`: Done/архив/удалённые сразу, остальные через 3 дня; только укорачивает включённые правила), `worktreeSaveChanges: true`.
- **Когда:** первый проход через 10 минут после старта, дальше раз в час; через 30 с после `thread.deleted`, через 11 минут после `thread.settled`/`thread.archived`; дешёвый statfs раз в 10 минут, при нехватке места - внеочередной проход (не чаще раза в 30 минут). Один воркер: проходы не пересекаются, в очереди максимум один автоматический.
- **Проверки (порт апстримного storage cleanup):** только `<baseDir>/worktrees/<repo>/<branch>` (realpath, ровно два уровня, не симлинк, внутри нет корня проекта), `.git` - файл, тот же репозиторий (common dir), та же ветка, есть коммит, нет `git worktree lock`, `index.lock`, сабмодулей, вложенных репозиториев; чат не работает и ничего не ждёт (сессия starting/running, активный ход, approval, вопрос, активность моложе 10 минут), нет открытого терминала и живой provider-сессии в копии, копию не делят два живых чата. Всё перечитывается ещё раз прямо перед удалением. Удаление - `git worktree remove` из основного checkout; `--force` только для копии с изменениями после сверки снимка с копией. Ветки не удаляются никогда.
- **Работа не теряется:** незакоммиченное (tracked + untracked, без ignored) - commit-снимок поверх HEAD в `refs/uno/saved/<threadId>` (временный индекс, как checkpoints); ignored `.env*` (кроме `node_modules`, до 50 файлов по 1 МБ) - в `<baseDir>/saved-worktrees/<threadId>/` (папки 0700, файлы 0600, manifest последним). Не сохранилось или не сошлось - копия остаётся, сохранённое откатывается. Копии с > 20 000 изменённых файлов или > 200 МБ незакоммиченного не трогаются.
- **Возвращение:** `ProviderCommandReactor.ensureSessionForThread` (следующее сообщение) и `terminal.open`/`restart` (терминал для worktree треда) зовут `ensureThreadWorktree`: `worktree prune` + `worktree add` той же ветки (удалённая ветка создаётся заново от базы снимка), снимок ложится назад незакоммиченными изменениями (`restore` на той же базе, иначе `cherry-pick --no-commit`; конфликт - копия чистая, ref остаётся, warning в лог), `.env*` назад (существующий файл не перезаписывается), затем ref и папка удаляются. Только для путей внутри `<baseDir>/worktrees`. `node_modules`/сборка не возвращаются - это сказано агенту в `agentContext/guides.ts`. Checkpoint-реактору хук не нужен: ensure идёт до старта сессии.
- **Провод:** capability `worktreeCleanup`; RPC `uno.computer.worktreeCleanupStatus` / `uno.computer.worktreeCleanupRun` (`StorageCleanupStatus`: последний отчёт, папка, идёт ли проход); `TerminalManager.listSessions()`. Отчёт только в памяти (последний проход), в Inbox/Telegram ничего не уходит, removed/failed пишутся в лог.
- **Web:** `components/settings/ChatCopiesCleanup.tsx` + `chatCopiesCleanup.logic.ts` - одна строка «Old chat copies are cleaned up automatically · last run freed …» в Settings → Computer, под свёрнутым Advanced переключатели, дни, «Clean up now» и последний отчёт; то же в dev-режиме на `EnvironmentGeneralSettings`. `environments/worktreeCleanupSupport.ts` - capability-хуки. `useThreadActions.ts`: новый демон с `worktreeOnDelete` сам уберёт копию удалённого чата, вопрос «Delete the worktree too?» не задаётся.
- **Агент:** `computer_cleanup` показывает копии чатов (`chatCopies`: папка, число, размер, последний проход) и в `apply` запускает проход (`only: ["chat-copies"]` - только его).
- **Компромиссы:** снимки и `.env*` удалённых чатов не удаляются никогда (ref + папка живут, пока их не уберут руками). Прочие ignored-файлы (локальные БД, `dist/`, `node_modules`) не сохраняются. Авто-Done на сервере не знает клиентских отметок «прочитано»: завершённый и непрочитанный чат после 3 дней тишины считается Done.
- **Тесты:** `worktreeCleanup/policy.test.ts`, `worktreeCleanup/WorktreeCleanup.test.ts` (реальный git во временном репозитории), `components/settings/chatCopiesCleanup.logic.test.ts`.

### Страницы, схемы и цитаты в чате (T3 port, волна 3, 30.10)

Агент отвечает не только текстом: страница с числами, таблицей или графиком прямо в ленте (свёрнутый ход её не прячет), кнопка на весь экран с зумом 50–200%, тема приложения. Mermaid-схемы рисуются в ответах, документах и файлах `.mmd`/`.mermaid`, библиотека (pele, 2,4 МБ) грузится только когда схема появилась.

- **Откуда:** `packages/shared/src/htmlRender.ts` и `themePalettes.ts` - копия T3 с правками; `HtmlFileFrame`, сервер на Effect AI и браузер превью написаны заново под нас. Кода на Effect из T3 здесь нет, поэтому разница версий (у T3 Effect новее нашего 4.0.0-beta.59) не мешает.
- **Инструменты:** `html_preview` (снимок страницы агенту до показа: своя временная копия Chromium, не профиль человека) и `html_render` (показать), `apps/server/src/unoWork/htmlTools.ts`, живут в общем наборе `uno-work`, поэтому работают у Claude, Codex и OpenCode одинаково. Оба уровня `safe`, карточки Allow нет.
- **Как страница попадает в чат:** демон кладёт файл `<attachmentsDir>/<id>.html` (0600) и сам пишет активность `html.render` в тред, разбирать события харнесса не нужно. `capThreadActivities` не даёт лимиту в 500 активностей вытеснить страницы. Приложение читает файл по обычному сокету `filesystem.readFile`, поэтому локально, на удалённом компьютере и в вебе путь один: без HTTP-маршрута, токена и CORS.
- **Картинки:** локальные (`src=`, `url()`: абсолютный путь, `~/`, `file:///`, относительный) вшиваются в страницу при публикации, отчёт переживает удаление файлов. Проверяются граница ассистента (после `realpath`) и сигнатура файла, до 10 МиБ на картинку, 25 МиБ на страницу.

**Правила песочницы** (`htmlRenderFrameDocument`, `HTML_RENDER_CSP`, проверка в настоящем браузере `apps/server/src/htmlRender/sandbox.integration.test.ts`):

1. Два вложенных `srcdoc`-фрейма, оба `sandbox="allow-scripts allow-forms"`, без `allow-same-origin`: origin пустой (`null`), у страницы нет адреса и токена. Два уровня нужны, потому что навигацию фрейма судит CSP родителя, а CSP приложения должен пускать сайты в панель; внешний документ наш, и его `frame-src 'none'` запрещает странице уйти на другой адрес.
2. Нет доступа к кукам, localStorage, IndexedDB, Service Worker, буферу обмена, DOM и адресу приложения.
3. Сеть: скрипты, стили и шрифты только с `cdn.jsdelivr.net`, `unpkg.com`, `cdnjs.cloudflare.com`, плюс Google Fonts. `fetch`, XHR, WebSocket, beacon, картинки, формы, всплывающие окна и вложенные адреса закрыты. Внешние картинки тоже: агент сохраняет файл и вшивает его.
4. WebRTC: `webrtc 'block'` Chrome не понимает, поэтому до кода страницы `RTCPeerConnection` убирается, вложенные фреймы удаляются `MutationObserver`, а окно десктопа работает с `setWebRTCIPHandlingPolicy("disable_non_proxied_udp")`. Сайты панели - отдельные `webContents`, их это не касается.
5. Приложение принимает от страницы только высоту, ссылку, клавиши и картинку, причём действия только по жесту человека и при фокусе на фрейме.

Что остаётся: `eval` внутри страницы разрешён (без него не работают библиотеки графиков), три CDN принимают любые пути, значит наружу можно вынести данные через адрес запроса к такому CDN, `<link rel=dns-prefetch>` браузер не отдаёт на проверку CSP, а в вебе страница, нарочно спрятавшая фрейм в закрытый shadow root, доберётся до WebRTC. Всё это касается только того, что уже есть на странице: токенов и данных приложения там нет.

**Цитата с замечанием:** выделил текст в ответе или на странице панели, кнопка Quote, комментарий (необязателен), чип у композера. Уходит с ближайшим сообщением, в том числе через «Up next» и outbox.

### Поток computers (волна T3→Work, 30.10)

- **Обновить всё (Settings → About, кнопка в уведомлении о версии).** `apps/web/src/updateEverything/`: план по всем компьютерам из `useMachineRows` (Work через существующий `/api/self-update/*`, агенты через существующий `provider.install.*`). Агенты раньше Work, компьютер, который отдаёт эту страницу, последним, приложение на Mac после всех; по 3 компьютера сразу. `GET /api/self-update/agents` (`apps/server/src/agentUpdates.ts`) сравнивает установленную версию с npm latest. OpenCode закреплён `UNO_OPENCODE_VERSION` (движок Uno Code), пин в трёх местах держит тест `agentUpdates.test.ts`. Образ менять не нужно. Спящий компьютер просыпается при запуске плана, строка в диалоге говорит об этом заранее.
- **Перенос проекта.** Пункт `Move to another computer…` в меню проекта (`dProjectMenu` в `Sidebar.tsx`), тот же `ContinueOnMachineDialog` с `moveProject`. Снимок берёт корень проекта (`scope: "project"`), чат-носитель выбирает `pickProjectMoveChat` (последний в корне, иначе последний). На цели, где проекта не было (`fresh`), файлы ложатся в корень на ветке источника (`placement: "project-root"`, `git checkout -B`), чат без worktree. Если проект там уже есть или папка уже была репозиторием, поведение прежнее: новый worktree, файлы человека не трогаем. Проект без чатов уходит в старый `MoveProjectToBoxDialog` (только клон и `.env`). `.env` и `.env.*` (`isCarriedEnvFileName`: без example/sample/template/dist) едут только с галочкой: в переносе проекта она включена, в переносе чата выключена. Только корень проекта, вложенные `apps/x/.env` не едут. Источник ничего не удаляет.
- **Страницы в переносе чата.** Страница (`html.render`) это файл в `attachmentsDir` источника; `orchestration/continuePages.ts` пакует их в JSON, второй transfer рядом с bundle (`pagesTransfer`), цель проверяет digest, сохраняет через `storePage` под новым чатом и добавляет активности после seed. Лимит `THREAD_CONTINUE_MAX_PAGES_BYTES` (256 МиБ) считается с самых новых страниц. Ошибка на любом шаге не роняет перенос, число оставшихся видно в тосте. Флаг `capabilities.threadContinuePages`: старая цель просто не получает страниц.
- **Закрепы приложений и виджетов.** Тонкий отдельный ряд под навигацией (`sidebar/SidebarPinRow.tsx`), виден только когда есть закрепы, лишнее в `More`. Виджет Home закрепляется как `kind:"app"`, `target:"uno-widget:<id>"`: новый `UnoPinKind` нельзя, неизвестное значение обнуляет все настройки при декодировании. Закрепы чатов это другой поток (`SidebarPinned.tsx`).
- **install.sh.** `resolve_bind_host`: явный `UNO_WORK_HOST` → значение из env-файла → `0.0.0.0` только на боксе (`/usr/local/sbin/uno-box-agent`) → иначе `127.0.0.1`. `deploy/prepare-image.sh` падает, если в образе loopback. Уже стоящие чужие машины с `0.0.0.0` при обновлении не меняются.
- **Bring your own.** `AddEnvModal`: честный текст и событие воронки `connect_path` с `props.card = "bring_your_own"`. Без аккаунтного транспорта событие не пишется.
- **Fix Work (меню аккаунта).** `POST /api/fix-work/prepare` (только владелец) кладёт в `<stateDir>/fix-work/<stamp>/` плейбук, контекст и очищенный хвост логов, веб открывает чат в режиме Ask. Письмо это тул `support_draft`: демон чистит секреты (`redactForSupport`) и показывает карточку, человек отправляет сам. Границы держат плейбук, Ask и очистка на демоне, песочницы нет.

### Поток newproject (волна T3→Work, 30.10)

- **No project.** Пункт в пикере нового чата и на Home (`NewChatFolderPicker`, `FolderChipMenu`). У компьютера один проект с корнем `~/chats` (`packages/shared/src/noProject.ts`), демон при bootstrap чата делает ему свою папку `~/chats/<дата>-<слова>` (`project/noProjectFolder.ts`, `noProjectChatFolder` в `ws.ts`). Ошибка папки отправку не ломает. Превращение в проект: прежний `thread.project.adopt`. Папки не чистятся, как и scratch у T3.
- **New project в пикере.** Тот же `NewProjectDialog`, шаг `empty`: имя (живёт в `newProjectStore`, чтобы не пропасть при смене компьютера), компьютер (`NewChatComputerPicker`, вместе с `activeEnvironmentId`), куда синкать (`projectDestinations`: Uno, подключённые GitHub/GitLab, только на этом компьютере). Upload и Clone идут по-старому.
- **Подключён = `server.discoverSourceControl`:** `gh`/`glab` на этом компьютере залогинены. GitHub App аккаунта здесь не считается.
- **Проект с репозиторием.** Порядок важен: `projectSync.startRepository` (git и первый коммит) до `project.create`, иначе папка навсегда останется snapshot. Потом `projectSync.connectHost` в фоне с тостом: приватный репозиторий, remote, `Stored.host`. `syncGit` обменивается с хостом через `exchangeHost` (`hostRemote`, `skipCloud`), провал хоста не останавливает Uno.
- **Ключи.** `SourceControlRepositoryService` до `createRepository` вызывает `PublishKeyCheck` (`keysBeforePublish` из `uno-sync`, вся история HEAD), ошибка проверки тоже запрещает публикацию. Дальше каждый push к хосту идёт через `keysLeavingWith` со своим кэшем `uno-held-<remote>.json`. Правка `uno-sync.mjs` требует `node apps/server/scripts/embed-app-sdk.ts`.
- **Демо:** `?hosts=github,gitlab` включает хосты, сценарий `apps/web/demo-e2e/newproject-shots.mjs`. Харнесс демо не кодирует ответы, поэтому void-RPC отвечает `null`: `undefined` выпадает из JSON.
